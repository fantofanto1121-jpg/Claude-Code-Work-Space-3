# 設計書

## 1. 技術スタックと選定理由

| 層 | 採用 | 理由 |
|----|------|------|
| 言語 | **Python 3.12** | あなたが学習済み。学べば読めるコードになる |
| Webフレームワーク | **FastAPI** | 型ヒントで引数の間違いに気づける。軽量で無料枠のメモリに収まる |
| 画面 | **Jinja2（サーバー側でHTML生成）** | React等を使わないので**ビルド工程が不要**。1つのサービスだけで完結する |
| ORM | **SQLAlchemy 2.0** | SQLを文字列連結せずに書ける＝SQLインジェクションが構造的に起きにくい |
| 本番DB | **PostgreSQL (Neon)** | 無料枠があり、アイドル後に**自動復帰**する |
| 開発DB | **SQLite** | インストール不要。`git clone` 直後に動く |
| 認証 | **自前サーバーサイド認証**（Argon2id + 署名付きCookie） | 下記参照 |
| ホスティング | **Render（無料プラン）** | GitHub連携でpushするだけ。常時HTTPS |
| メール | **Resend**（任意） | 未設定でもアプリは動く（ログ出力に切り替わる） |

### なぜ React ではなく Jinja2 か

初心者が1人で保守する前提では、**動く場所が1つ**であることが何より重要です。
React を使うと「フロント用のビルド」「API設計」「CORS」「2つのデプロイ先」が増え、
不具合が起きたときの切り分けが一気に難しくなります。
掲示板は文章が主役なので、サーバーでHTMLを作る方式で十分です。

副次的な利点として、外部スクリプトを一切読み込まないため、
CSP（コンテンツセキュリティポリシー）を強く設定でき、XSS に対してさらに堅くなります。

### なぜ Supabase Auth ではなく自前認証か

当初 Supabase（認証＋DB）も検討しましたが、**無料プランは7日間アクセスが無いとプロジェクトが
一時停止し、ダッシュボードから手動で復帰させる必要があります**。
個人運営の小さな掲示板ではアクセスが途切れる日があるため、
「ある朝サイトが落ちている」という状態になりやすく、採用を見送りました。

Neon は自動で復帰するため、この問題がありません。
ただし Neon には認証機能が無いので、認証は自前で実装しています。
ここで言う「自前」は**暗号処理を自作するという意味ではありません**。

- パスワードのハッシュ化 → `argon2-cffi`（Argon2id。パスワードハッシュ競技会の優勝方式）
- セッションCookieの署名 → `itsdangerous`（Flask 作者による実績あるライブラリ）

危険なのは「ハッシュ関数や署名を自分で書くこと」であって、
検証済みライブラリを正しい手順で組み合わせることは、標準的で安全なやり方です。

### 検討したが採用しなかったもの

| 候補 | 見送った理由 |
|------|--------------|
| Supabase | 無料枠は7日無アクセスで一時停止、手動復帰が必要 |
| Fly.io | 2026年時点で実質的な常時無料枠が縮小。クレジットカード必須 |
| Railway | 無料は試用クレジットのみで、使い切ると停止 |
| Vercel + Serverless | Python の常時接続DBと相性が悪く、コネクション枯渇を起こしやすい |
| PythonAnywhere 無料 | 外部への通信が制限され、独自ドメインが使えない |

## 2. ディレクトリ構成

README の「フォルダの中身」を参照してください。設計の意図は以下のとおりです。

```
ブラウザ
   ↓
routers/    … HTTPを受けて、どの画面を返すか決めるだけ
   ↓
deps.py     … ログイン判定・権限チェック（ここを必ず通す）
   ↓
services.py … 入力検証とビジネスロジック（テストしやすいようDBと画面から分離）
   ↓
models.py   … テーブル定義
   ↓
データベース
```

**層を分ける理由**: 権限チェックを `deps.py` の1か所に集めることで、
「このページだけチェックを書き忘れた」という事故を防げます。

## 3. データベース設計

### テーブル一覧

| テーブル | 役割 |
|----------|------|
| `users` | 会員。メールアドレス、パスワードハッシュ、表示名、権限 |
| `categories` | カテゴリー |
| `threads` | スレッド |
| `posts` | 投稿（スレッド本文も返信も、すべてここ） |
| `reports` | 通報 |
| `moderation_actions` | 管理操作の履歴 |
| `email_tokens` | パスワード再設定・メール確認のトークン |
| `rate_limit_hits` | 連投・総当たり攻撃の抑制用カウンタ |
| `schema_migrations` | 適用済みマイグレーションの記録 |

### 関係

```
categories ──< threads ──< posts ──< reports
                  │          │
users ────────────┴──────────┘
users ──< email_tokens
users ──< moderation_actions (admin_user_id)
```

### 設計上の重要な判断

**(a) 投稿番号の一意性**

`posts` に `UNIQUE (thread_id, post_number)` を設定しています。
さらに採番のたびに、PostgreSQL では `SELECT ... FOR UPDATE` でスレッド行をロックします。
万一衝突しても、`services.add_post()` が最大4回まで採番をやり直します。
この動作は `tests/test_concurrency.py` で検証しています。

**(b) 物理削除せず、論理削除する**

投稿を本当に消すと `>>5` のような返信先がずれ、会話が読めなくなります。
そのため `is_deleted` フラグを立て、本文のかわりに
「この投稿は投稿者本人により削除されました」と表示します。
番号は欠番にしません。

**(c) 集計値をスレッド行に持つ（非正規化）**

一覧表示のたびに投稿数を数えると遅くなるため、
`threads.post_count` と `threads.last_posted_at` を投稿時に更新しています。

**(d) 内部IDと公開表示名の分離**

`users.id`（内部）と `users.display_name`（公開）を分けています。
メールアドレスは公開画面のテンプレートに一切登場しません。

**(e) 日時はすべて UTC で保存**

保存は UTC、表示時に日本時間（+9時間）へ変換します（`app/utils.py`）。
こうしておくと、将来サーバーの地域を変えても表示が狂いません。

### インデックス

| 目的 | インデックス |
|------|--------------|
| カテゴリー別の最新順一覧 | `(category_id, is_deleted, last_posted_at)` |
| 全体の最新順・新着順・人気順 | `(is_deleted, last_posted_at)` 他 |
| スレッド内の投稿表示 | `(thread_id, post_number)` |
| マイページの投稿一覧 | `(user_id, created_at)` |
| 本文検索（PostgreSQLのみ・任意） | `migrations/002_search_index.postgresql.sql`（pg_trgm） |

### 検索について

日本語は英語と違って単語が空白で区切られないため、
PostgreSQL 標準の全文検索（`to_tsvector`）はそのままでは日本語を正しく分割できません。
そこで本プロジェクトでは、確実に動く**部分一致検索（ILIKE）**を採用しています。

データが増えて遅くなった場合は、`migrations/002_search_index.postgresql.sql` の
pg_trgm インデックスを適用してください（Neon で利用できるか要確認）。

## 4. 画面設計と配色

### 配色（`app/static/css/style.css` の `:root`）

| 用途 | 変数 | 値 |
|------|------|-----|
| 背景 | `--bg` | `#FAF7F2` |
| カード背景 | `--surface` | `#FFFFFF` |
| メインカラー | `--primary` | `#B8324A` |
| ホバー | `--primary-hover` | `#92263A` |
| 薄いアクセント | `--primary-soft` | `#F4E2E4` |
| 本文 | `--text` | `#292524` |
| 補助文字 | `--text-muted` | `#78716C` |
| 罫線 | `--border` | `#E8E1DA` |

色を変えたいときは、この `:root` の値だけを書き換えてください。全画面に反映されます。

### UIの方針

- 余白は 4px の倍数（`--space-1` 〜 `--space-8`）に統一
- 角丸は 4 / 8 / 12px の3段階のみ
- 影は3段階で、いずれも極薄
- ルージュは「主要ボタン」「選択中のタブ」「レス番号」「アクセント」にのみ使用
- グラデーション・派手なアニメーションは不使用
- 絵文字は不使用。アイコンはすべてインラインSVG
- 状態は**色だけで表さない**（「返信締切」バッジ、エラーの「！」記号など文字・記号を併記）

### 日本語タイポグラフィ

- フォント: ヒラギノ角ゴ → BIZ UDPGothic → 游ゴシック → Meiryo の順でフォールバック
- 本文の行間 1.9、見出し 1.45（日本語は行間を広めに取ると読みやすい）
- 字間 `letter-spacing: 0.02em`
- 本文幅は最大 960px（1行が長くなりすぎると読みにくいため）

### レスポンシブ

| 画面幅 | 変化 |
|--------|------|
| 901px 以上 | ヘッダーに検索窓、2カラム表示 |
| 900px 以下 | ヘッダー検索を隠す、1カラム |
| 640px 以下 | ボタンを 42px 以上に拡大、**右下に「スレッド作成」固定ボタン**（親指が届く位置）、余白を圧縮 |

### 各状態のデザイン

| 状態 | 対応 |
|------|------|
| ローディング | `.skeleton`（送信中はボタンを `.is-submitting` に） |
| 空データ | `.empty`（アイコン＋説明＋次の行動ボタン） |
| エラー | `.notice--error` と `.field__error`（「！」記号つき） |
| 成功 | `.notice--success`（「完了」ラベルつき） |
